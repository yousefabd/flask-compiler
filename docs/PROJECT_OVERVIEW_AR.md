# شرح كامل لمشروع مترجم miniFlask (بالعربية)

## ما هو هذا المشروع؟

هذا المشروع هو **مُتَرجِم (Compiler) تعليمي** مكتوب بلغة **Java** باستخدام مولّد المحلّلات **ANTLR 4**.

اللغة المصدرية التي يترجمها المشروع اسمها **miniFlask**، وهي عبارة عن:

* ملف **Python/Flask** (الواجهة الخلفية Backend) — مثل `tests/app.py`
* قوالب **HTML + Jinja2** (الواجهة الأمامية Frontend) — مثل `tests/templates/index.html`
* ملفات **CSS** للتنسيق — مثل `tests/static/styles.css`

المترجم يقرأ هذه الملفات، يحلّلها لغويًا ودلاليًا عبر مرحلة **Resolver** (محلّل قيم)، ثم — إن لم توجد أخطاء — **ينتج نوعين من المخرجات من نفس المدخلات**:

1. **مشروع Flask حقيقي قابل للتشغيل** في مجلد `generated/`:
   ```
   python generated/app.py
   ```
2. **موقع ثابت (Static Site) خالٍ تمامًا من Jinja** في مجلد `output/`، بالإضافة إلى مخرجات تحليلية في `compiler_output/` — صفحة HTML نهائية واحدة لكل مسار (route)، حيث تُقيَّم كل عبارات `{% if/for %}` و `{{ expr }}` وتُستبدَل بقيمها وقت الترجمة، وليس عند التشغيل.

بمعنى آخر: المشروع "مترجم من miniFlask إلى Python + HTML"، والـ **AST (شجرة التركيب المجرّدة)** هي التمثيل الوسيط بين كل المراحل.

## مراحل المترجم (Pipeline)

```
الكود المصدري (app.py + templates/*.html)
        │
        ▼
1) التحليل اللفظي (Lexer)          ← تقسيم النص إلى Tokens
        │
        ▼
2) التحليل النحوي (Parser)         ← بناء شجرة الإعراب (Parse Tree) حسب القواعد g4
        │
        ▼
3) بناء الـ AST (Visitors)          ← تحويل شجرة الإعراب إلى شجرة تركيب مجردة نظيفة
        │
        ▼
4) التحليل الدلالي (Semantic)      ← جدول الرموز + كشف الأخطاء الدلالية + فحص الأنواع
        │
        ▼
5) الـ Resolver                    ← ربط كل قراءة لمتغيّر بتعريفه + تتبّع القيم الثابتة وقت الترجمة
        │
        ▼
6) توليد الكود (Code Generation)   ← مساران متوازيان من نفس الـ AST:
        │                             أ) مشروع Flask تنفيذي (generated/)
        │                             ب) موقع HTML ثابت خالٍ من Jinja (output/)
        ▼
```

كل مرحلة محاطة بـ **حاجز أخطاء (Error Boundary)**: أي خطأ نحوي أو دلالي أو خطأ توليد يُجمَع في تقرير موحّد ولا يُسقِط البرنامج أبدًا.

## هيكل المشروع والملفات

### 1) مجلد `grammars/` — قواعد اللغات (ANTLR Grammar)

| الملف | الوظيفة |
|---|---|
| `python/PythonLexer.g4` + `PythonParser.g4` | قواعد لغة Python المصغّرة: الدوال، الشروط، الحلقات، الاستيراد، الـ decorators (مثل `@app.route`)، التعابير الحسابية والمنطقية، القوائم والقواميس... |
| `html/HTMLLexer.g4` + `HTMLParser.g4` | قواعد HTML مع دعم عبارات Jinja2 داخلها (`{{ }}` و `{% %}`) |
| `jinja2/Jinja2Lexer.g4` + `Jinja2Parser.g4` | قواعد تعابير Jinja2 |
| `css/CSSLexer.g4` + `CSSParser.g4` | قواعد CSS (المحدّدات Selectors والخصائص Declarations) |

### 2) مجلد `src/antlr/` — الأصناف المولّدة من ANTLR

أصناف الـ Lexer والـ Parser والـ Visitor الأساسية المولَّدة تلقائيًا من ملفات `.g4` (لا تُعدَّل يدويًا).

### 3) مجلد `src/python/` — خط أنابيب لغة Python

| المكوّن | الوظيفة |
|---|---|
| `models/` | أصناف عقد الـ AST: `Program`, `FunctionDef`, `IfStatement`, `ForStatement`, `WhileStatement`, `DecoratorStatement`, `BinaryExpression`, `IDTrailer`, والذرّات (`IntegerAtom`, `StringAtom`, `List`, `Dictionary`, ...) — كل عقدة تحفظ بياناتها ورقم السطر وأبناءها |
| `visitor/PythonVisitor.java` | يحوّل شجرة إعراب ANTLR إلى AST |
| `symbol_table/` | جدول الرموز: `Scope`, `Symbol`, `SymbolTable`, `SymbolTableBuilder` — يبني النطاقات (global / function / for / while / if) ويعرّف المتغيرات والدوال والمعاملات، ويدعم عبارة `global`، ويكشف 6 أخطاء دلالية (دالة/معامل مكرر، `return`/`break`/`continue` خارج سياقه، `global` عديم الأثر) |
| `resolver/PythonResolver.java` | **مرحلة الـ Resolver**: تمرّ مرة ثانية على الـ AST بجدول رموز مستقل، وتربط كل *قراءة* لمعرِّف بتعريفه (شيء لا يفعله `SymbolTableBuilder` أبدًا، لأنه لا يزور الشروط ولا الحلقات ولا الطرف الأيمن من التعبير)، وتكتشف المتغيرات غير المعرّفة فعليًا، وتتتبّع قيمًا ثابتة معروفة وقت الترجمة (تُلغى القيمة فور إعادة إسناد غير حرفية أو استدعاء مُغيِّر مثل `.append(...)`) |
| `printer/ASTPrinter.java` | طباعة الـ AST على شكل شجرة للأغراض التعليمية |

### 4) مجلد `src/jinja2/` — خط أنابيب القوالب (HTML + Jinja2)

| المكوّن | الوظيفة |
|---|---|
| `models/` | عقد AST القوالب: `TemplateFile`, `HtmlTextNode`, `OutputNode` (أي `{{ expr }}`), عناصر HTML العادية والفارغة، الخصائص Attributes، وعبارات `ForStatementNode`, `IfStatementNode`, `SetStatementNode`, `MacroStatementNode`, `BlockStatementNode`, `ExtendsStatementNode`, `IncludeStatementNode`، والتعابير (وصول لخاصية، فهرسة، استدعاء، فلاتر `|length` ...) |
| `visitor/AntlrToTemplateAstVisitor.java` | يحوّل شجرة إعراب HTML/Jinja إلى AST |
| `symbol_table/` | جدول رموز القوالب: `Symbol` يحمل الآن قيمة العبارة المُعرَّفة (`ExpressionNode`) ونوعًا مُستنتَجًا (`SymbolType`)، بالإضافة إلى قيمة مُحلَّلة إضافية (`resolvedValue`) وأسطر الاستخدام (`usageLines`) أضافتها مرحلة الـ Resolver؛ و`SymbolTableBuilder` يعرّف النطاقات **ويحلّل القراءات** في نفس الوقت |
| `resolver/TemplateResolver.java` | واجهة تقرير بسيطة (وليست مسحًا ثانيًا للشجرة) فوق ما التقطه `SymbolTableBuilder` فعلًا أثناء تحليله |
| `symbol_table/semantic_rules/` | قواعد دلالية قابلة للإضافة (نمط Strategy): `UlLiRule` (فحص أن `<li>` داخل `<ul>`)، و`TypeCheckerRule` (فحص أنواع كامل ومنفصل: عمليات ثنائية/أحادية، استدعاءات، فهرسة، خصائص) مع `SemanticContext` |

### 5) مجلد `src/css/` — خط أنابيب مساعد

بناء AST لملفات CSS وجدول رموز خاص به — مادة تعليمية مساعدة، ليست جزءًا من مسار `compile()` الرئيسي.

### 6) مجلد `src/errors/` — إطار معالجة الأخطاء الموحّد

| الصنف | الوظيفة |
|---|---|
| `CompilerStage` | مرحلة الخطأ: `PARSING`, `SEMANTIC_ANALYSIS`, `CODE_GENERATION`, `IO` |
| `CompilerException` | الأب المجرد لكل أخطاء المترجم (يحمل المرحلة + الملف + السطر) |
| `ParseError` / `SemanticError` / `CodeGenError` | استثناءات لكل مرحلة |
| `CompilerProblem` | سجل خطأ موحّد قابل للطباعة بصيغة `[KIND] file line N: message` |
| `ErrorReporter` | المجمّع المركزي: يستقبل أخطاء بايثون وأخطاء Jinja2 والاستثناءات، وينسّق تقريرًا واحدًا (يُطبع على الشاشة **ويُعاد استخدامه حرفيًا** داخل `compiler_output/semantic_report.txt`) |
| `SyntaxErrorListener` | مستمع ANTLR يلتقط الأخطاء النحوية بدل طباعتها على الشاشة، فلا يُبنى AST من شجرة معطوبة |

### 7) مجلد `src/resolver/` — نموذج القيمة المشترك

| الصنف | الوظيفة |
|---|---|
| `ConstantValue.java` | قيمة ثابتة معروفة وقت الترجمة: `INT\|FLOAT\|STRING\|BOOL\|NONE\|LIST\|DICT\|UNKNOWN` — يستخدمها الـ Resolver في كلا الجانبين، وميزة "الطي" (folding) في مولّد القوالب، ومولّد الموقع الثابت |
| `PythonLiteralEvaluator.java` | منطق مطابقة القيم الحرفية في بايثون (مستخرَج من `PythonResolver` ليُعاد استخدامه دون تكرار)، يستخدمه أيضًا `codegen.ModuleContextExtractor` |

### 8) مجلد `src/codegen/` — مولّدات الكود والتنسيق

| الصنف | الوظيفة |
|---|---|
| `PythonCodeGenerator.java` | يمشي على AST بايثون ويولّد كود Python تنفيذي، ويحقن معالجات أخطاء وقت التشغيل (`@app.errorhandler(404)` و `@app.errorhandler(Exception)`) قبل حارس `if __name__ == "__main__"` |
| `TemplateCodeGenerator.java` | يولّد HTML/Jinja2 **حي** (لملفات `generated/`، حيث تبقى `{% if/for %}` كما هي لأن بياناتها لا تُعرف إلا عند وصول طلب حقيقي)، مع وضع اختياري "للطي" (folding) لمعاينات `generated/rendered/` |
| `ModuleContextExtractor.java` **(جديد)** | يستخرج من الـ AST مستوى الوحدة فقط (module-level) القيمة **الابتدائية** الحرفية لكل متغيّر (مثل `products = [...]`)، متجاهلًا ما يفعله أي مسار (route) بها لاحقًا وقت التشغيل — وهذا يختلف عمدًا عن `PythonResolver` الذي يُلغي القيمة بمجرد رؤية `.append(...)` في أي مكان بالبرنامج (سلوك صحيح لغرضه، خاطئ لغرض توليد موقع ثابت) |
| `RouteTable.java` **(جديد)** | يقرأ كل `@app.route(...)` من الـ AST ويحوّله إلى خريطة "اسم الدالة ← نمط الرابط"، لحلّ استدعاءات `url_for(...)` إلى مسارات فعلية وقت الترجمة |
| `StaticPageGenerator.java` **(جديد)** | يمشي على AST القالب **ويُقيِّم** بدل أن يُعيد كتابة Jinja: يفكّ حلقات `{% for %}` بالكامل، يختار الفرع الصحيح من `{% if/elif/else %}` فقط، يستبدل `{{ expr }}` بقيمتها (مع الهروب HTML كما يفعل Jinja افتراضيًا)، ويحلّ `url_for(...)` والفلاتر الشائعة. أي شيء لا يمكن إثباته (بيانات وقت التشغيل، أو `{% extends/include %}`) يُترك كتعليق HTML ظاهر ومُسجَّل في السجل — لا تخمين ولا انهيار أبدًا |
| `AstJsonWriter.java` **(جديد)** | كاتب JSON بسيط بلا أي مكتبة خارجية، لتفريغ شجرتَي AST (بايثون وJinja) في `compiler_output/` |
| `FlaskProjectGenerator.java` | **قائد المشروع كاملًا**: يفسّر `app.py`، يكتشف القوالب المستدعاة عبر `render_template(...)`، يحلّلها دلاليًا، ثم يُنتج **كلا المخرجين**: المشروع التنفيذي في `generated/`، والموقع الثابت + مخرجات التحليل في `output/` و `compiler_output/` — وكل ذلك خلف حاجز أخطاء واحد |

### 9) `src/Main.java` — نقطة الدخول

يحتوي دوال تجريبية لكل خط أنابيب (`python()`, `jinja()`, `types()`, `css()`) بالإضافة إلى الدالة **`compile()`** التي تشغّل الترجمة الكاملة من المصدر إلى كلا المخرجين.

### 10) مجلد `tests/` — البرنامج المصدري (مدخلات المترجم)

| الملف | المحتوى |

| `app.py` | تطبيق "متجر منتجات" كامل بـ Flask: قائمة منتجات، دوال بحث/حذف/أكبر معرّف، ومسارات `/` و `/products` و `/product/<id>` و `/add` (GET+POST) و `/delete/<id>` مع رسائل flash |
| `templates/index.html` | قالب واحد متعدد الصفحات (رئيسية، قائمة المنتجات، تفاصيل منتج، إضافة منتج) باستخدام `{% if %}` و `{% for %}` و `{% set %}` والفلاتر |
| `templates/variables.html`, `types.html`, `scopes.html`, `ulli.html`, `attr_value.html` | قوالب تجريبية لاختبار جدول الرموز وفحص الأنواع والقواعد الدلالية |

## أهم المزايا (Features)

1. **أربع لغات مدعومة بالتحليل**: Python، HTML، Jinja2، CSS — لكل منها Lexer/Parser/AST خاص.
2. **جداول رموز حقيقية** بنطاقات متداخلة (global / function / loop / macro / block) مع دعم `global` في بايثون ومتغير `loop` السحري في Jinja.
3. **مرحلة Resolver حقيقية** على الجانبين: تربط كل معرِّف بتعريفه، تكتشف متغيرات غير معرّفة كانت تمر مرور الكرام سابقًا، وتتتبّع قيمًا ثابتة وقت الترجمة.
4. **فحص أنواع** في القوالب (`TypeCheckerRule`): كشف العمليات غير الصالحة، الاستدعاءات على قيم غير قابلة للاستدعاء، الفهرسة/الخصائص غير الصالحة.
5. **قواعد دلالية قابلة للتوسعة** (واجهة `ISemanticRule`).
6. **تحليل دلالي واعٍ بـ Flask**: فحص "متغير غير معرّف" **عابر للملفات** بين Python و HTML عبر استدعاءات `render_template`.
7. **مساران للتوليد من نفس الـ AST**:
   * مشروع Flask تنفيذي حقيقي (`generated/`).
   * **موقع HTML ثابت خالٍ تمامًا من Jinja** (`output/`) — الحلقات مفكوكة، الشروط محسومة، `url_for` محلول إلى مسارات فعلية، بلا أي اعتماد على تشغيل Flask.
8. **معالجة أخطاء شاملة**: أخطاء نحوية (`SyntaxErrorListener`)، دلالية (من بايثون وJinja معًا)، توليد/إدخال-إخراج (`CodeGenError`)، وحارس أخير لأي استثناء غير متوقع — ولا شيء يُسقط البرنامج.
9. **أمان وقت التشغيل في التطبيق المولَّد**: صفحات 404 و 500 ودّية بدل شاشة traceback.
10. **شفافية بدل التخمين**: أي قيمة لا يمكن إثباتها وقت الترجمة (بيانات طلب حقيقي، فلتر غير مدعوم) تظهر كتعليق HTML واضح ومُسجَّل، لا تُخمَّن ولا تُسقِط التوليد.

## الاختبارات والتحقق (ما تم فحصه فعليًا)

### أ) المسار التنفيذي (Happy Path)

* ترجمة `tests/app.py` + `index.html` نجحت بدون أي خطأ.
* الملف المولَّد `generated/app.py` **اجتاز فحص بايثون الحقيقي** (`python -m py_compile`).
* تشغيل التطبيق المولَّد عبر Flask test client: كل المسارات تعمل، الإضافة والحذف يعملان فعليًا، رسائل flash تظهر، و404 من المعالج المولَّد.

### ب) المسار الثابت (Static Site)

* **لا يوجد أي `{% %}` أو `{{ }}`** في أي من صفحات `output/*.html` الأربع (تم التحقق بفحص نصي مباشر).
* حلقة `{% for product in products %}` تحوّلت فعليًا إلى ثلاث بطاقات منتج منفصلة، مع روابط `url_for` محلولة (`/product/1`, `/delete/2`, ...) وأسعار منسَّقة عبر `"%.2f"|format(...)`.
* الصفحة الوحيدة التي تعتمد على بيانات وقت التشغيل الحقيقي (`product_details`، حيث `product` يأتي من دالة بحث بمعرِّف الطلب) تُظهر بصدق تعليق HTML مُسجَّلًا بدل اختلاق منتج وهمي.
* كلا ملفَي `compiler_output/ast_*.json` صالحان بصيغة JSON فعليًا (تم التحقق بتحميلهما عبر بايثون).
* `output/app.py` مُنسوخ **مطابق تمامًا** لمصدره (تم التحقق بـ `diff`).

### ج) مسارات الأخطاء

| الحالة | النتيجة |
|---|---|
| خطأ نحوي في `app.py` | تقرير `[SYNTAX] ...` — بدون انهيار |
| أخطاء دلالية متعددة (دالة مكررة، `return` خارج دالة...) | كل الأخطاء تظهر بأنواعها وأسطرها في تقرير واحد |
| متغير غير معرّف حقًا (اكتشفه الـ Resolver) | `[UNDEFINED_VARIABLE] ...` — لم يكن يُكتشف قبل إضافة الـ Resolver |
| فلتر غير مدعوم في المسار الثابت | يتحوّل إلى نص فارغ مع تسجيل الأمر في `generation_log.txt`، والتوليد يكمل بنجاح |

في كل حالات الفشل الحقيقية: `success = false` + تقرير مجمّع، **ولم يُولَّد أي ملف ناقص أو تالف**.

## كيف تشغّل المشروع؟

```bash
# 1) الترجمة (من جذر المشروع، مع مسار jar الخاص بـ ANTLR)
javac -encoding UTF-8 -cp antlr-4.13.2-complete.jar -d out $(find src -name "*.java")

# 2) تشغيل المترجم (ينفّذ Main.compile)
java -cp "out;antlr-4.13.2-complete.jar" Main

# 3أ) تشغيل التطبيق التنفيذي
python generated/app.py
# ثم افتح http://127.0.0.1:5000

# 3ب) أو فتح الصفحات الثابتة مباشرة — بلا حاجة لأي عملية بايثون
#     output/index.html, output/view_products.html, ...
```

## الخلاصة

المشروع مترجم تعليمي متكامل يغطي دورة الترجمة كاملة: **قواعد لغوية → تحليل لفظي ونحوي → AST → جداول رموز وتحليل دلالي وفحص أنواع → Resolver → توليد كود**، مع إطار معالجة أخطاء موحّد يجعل المترجم لا ينهار مهما كانت المدخلات سيئة. الميزة الفريدة هي إنتاج **مخرجين مختلفين تمامًا من نفس شجرة الـ AST**: تطبيق Flask تنفيذي حقيقي يعمل في المتصفح بنفس سلوك البرنامج المصدري، **وموقع HTML ثابت خالٍ تمامًا من Jinja** يمكن فتحه مباشرة بلا أي تشغيل لبايثون — مع شفافية كاملة في كل مكان لا يستطيع المترجم فيه إثبات قيمة ما، بدل التخمين أو الانهيار.
